# ReServe合宿 — 技術で売上を作るGTMエンジニア研修

仮想の美容室予約SaaS「**ReServe**」を題材に、**経営課題をデータ（SQL）で診断し、限られた予算をどこに投資すれば一番リターンが大きいかをROIで決める**一日合宿のリポジトリです。

受講生はこのリポジトリを clone するだけで、課題が仕込まれた**ローカルDB（Supabase）**と、画面の体感用**モック（静的HTML）**を各自のPCで立ち上げ、当日のワークに入れます。

## 課題：両側から漏れるバケツ

ReServeは美容室向けの予約管理SaaS。収益は**店舗の月額サブスク（固定）＋予約決済の1%手数料（変動）**の2本柱です。

営業は順調で**新規契約は来ている**。それでもサブスクも手数料も、計画ほど伸びない。入口は開いているのに溜まらない——**どこに穴が空いているか**をSQLで突き止め、ROIで投資先を決めるのが今日のミッションです。

> 何%詰まっているか、なぜ詰まっているかはここには書きません。**自分でSQLを叩いて見つける**のがワークの本体です。状況の全体像は [`00_シナリオ.md`](docs/事前設計/受講生向け/00_シナリオ.md) から読み進めてください。

## クイックスタート

> 前提：**Docker Desktop**（起動して常駐）／**Supabase CLI**／**Git** が入っていること。
> 入っていない場合のインストール手順は [`docs/事前設計/受講生向け/01_環境構築.md`](docs/事前設計/受講生向け/01_環境構築.md) にあります。

### 1. リポジトリを clone する

```bash
git clone https://github.com/SeiyaHirata/gtm-engineer-bootcamp.git
cd gtm-engineer-bootcamp
```

以降のコマンドは**すべてこのリポジトリ直下**で実行します。

### 2. ローカルSupabaseを起動する

ローカルSupabaseは **Docker コンテナ上**で動きます。`supabase start` の**前に** Docker Desktop を起動しておいてください。

1. **Docker Desktop を起動する**（アプリ一覧から起動）
2. メニューバー（macOS）／タスクトレイ（Windows）の**クジラアイコンが「Running」**になっていることを確認する
3. 起動していないと `Cannot connect to the Docker daemon` 等で `supabase start` が失敗します

任意の確認（エラーが出なければOK）：

```bash
docker info
```

問題なければ、リポジトリ直下で：

```bash
supabase start
```

- 初回はDockerイメージのダウンロードで数分かかります（2回目以降は速い）。
- `config.toml` の `[db.seed]` が有効なため、起動時に migrations 適用後 `seed.sql` が自動投入されます。
- 完了すると接続情報が表示されます。**Studio URL = http://localhost:54323** を控えておきます。
- 「確実にまっさらから入れ直したい」ときは `supabase db reset`（migrations＋seedを流し直す）。
- Docker のインストール・トラブル時は [`01_環境構築.md`](docs/事前設計/受講生向け/01_環境構築.md) を参照。

### 3. Supabase Studio で動作確認（500なら成功）

ブラウザで **http://localhost:54323** を開き、左メニューの **SQL Editor** で実行：

```sql
SELECT COUNT(*) FROM stores;
```

結果が **`500`** なら環境構築は成功です。全テーブルをまとめて検算するSQLは環境構築ドキュメントにあります。

### 4. モック（画面イメージ）をブラウザで開く

`mock/` 配下の静的HTMLを**ダブルクリック**で開くだけ（サーバー不要）。

```bash
# macOS の例
open mock/user/U-02_form.html
# Windows の例
start mock\user\U-02_form.html
```

| ファイル | 画面 | 面 |
|---|---|---|
| `mock/admin/A-01_onboarding.html` | 店舗オンボーディング | 店舗側（管理画面） |
| `mock/admin/A-03_dashboard.html` | 店舗ダッシュボード | 店舗側（管理画面） |
| `mock/user/U-01_store.html` | 公開店舗ページ | 利用者側（予約サイト） |
| `mock/user/U-02_form.html` | 初回予約フォーム | 利用者側（予約サイト） |
| `mock/user/U-03_confirm.html` | 予約確認 | 利用者側（予約サイト） |

### 5. シナリオから始める

ここまで動いたら、受講生向けドキュメントの先頭から読み進めます。

→ [`docs/事前設計/受講生向け/00_シナリオ.md`](docs/事前設計/受講生向け/00_シナリオ.md)

## 注意

- **詰まりの数字はSQLで出す。** 通過率・キャンセル件数・継続店舗数・GMV・手数料は、すべて `stores` / `billing_periods` / `reservations` / `payments` / `checkins` を `COUNT` / `GROUP BY` / `HAVING` / `SUM` / `AVG` で算出します。
- **モックの数字は仮（演出用）。** 例えばダッシュボードの「キャンセル18件」はレイアウト確認用の数字で、DBの実データ（実数はSQLで出す）とは無関係です。モックの表示数字から詰まりを判断してはいけません。
- シードは決定論的なので、**何度 `supabase db reset` しても同じ件数・同じ数字**になります。データが変だと思ったら、まずこれで入れ直してください。
