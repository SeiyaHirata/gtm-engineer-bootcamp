# 技術で売上を作るGTMエンジニア編 合宿（実践ワーク）｜ 要件・進め方

## 目的

- 第1回（全体像・基礎編）・第2回（データ分析編）で **見せた／教えた** ことを、受講生が **自分の手で実際にやる** 回。
- 第2回は実例デモに絞り「演習は入れない」方針だった（最終章ch16で「次回は合宿——手を動かして実践する」と予告済み）。その回収が合宿。
- ゴール：受講生が **ローカルのDBに対して自分でSQLを書き、ファネルに数字を当てて詰まりを特定し、施策を工数×インパクトで優先度づけして「明日からやる1手」まで出せる** 状態になる。
- 「分かる」から「できる」へ。座学では潰せない「自分の環境で手が止まる」を、その場で全部潰す。

## 合宿の前提（ユーザー決定済み）

- **形式：1日集中・オフライン**（半日〜1日で完結。手を動かす時間を最大化し、その場でフィードバックする）。
- **題材データ：ローカルのSupabaseエミュレーター**。受講生各自のマシンに `supabase start`（Docker）でローカルのPostgres＋Studioを立て、共通のシードデータ（ECの注文テーブル等）を投入して全員同じデータで進める。
  - 本物のサービスDBは使わない（環境差・権限・個人情報の事故を避ける）。まず共通サンプルで「型」を身につけることを優先。
  - 現行ワークフロー（要確認しながら手順書化）：`supabase init` → `supabase start` → `supabase/seed.sql` が `supabase start` / `supabase db reset` 時に流れる → Studio（既定 localhost:54323）またはSQLでクエリ。
- **保存先：本ファイル**（第2回 `要件.mdx` と同じディレクトリ。合宿用の要件mdxとして作成）。

## 進め方（作業ステップ・ゲート方式）

第2回と同じく、各ステップで一度止めて合意を取りながら進める（いきなり全部作り込まない）。

1. **要件を固める**（このドキュメント）← いま此処
2. **1日のタイムテーブルとワークの段取りを合意**（下の「構成案の叩き」を添削）
3. **環境構築手順を確定**（`supabase start` 〜 シード投入までを、環境に何も入っていない前提で再現できる手順書に。Docker/Supabase CLIの導入から）
4. **シードデータを設計・作成**（`seed.sql`。第2回の数字感＝詰まりが意図的に作り込まれたECデータ。`orders` / `users` 等）
5. **各ワークの課題文・模範クエリ・解説を執筆**（ワークシート）
6. **当日の進行台本に落とす**（タイムキープ、つまづきポイントの先回り）
7. **レビュー**（平田さん確認 → 必要ならCodex/別Claudeでレビュー）

> 中身（ワーク本文・シードの具体・模範解答）は手順3以降。この段階では触らない。

## 参照するコンテンツ（決定）

- **第2回 データ分析編**（`2.データ分析編.mdx` 本体／`2.データ分析編_原稿バックアップ_2026-06-17.md`）= 合宿で「やる」内容の出典。特に：
  - ch8 ファネルに数字を当てて詰まりを見つける（例：登録100→アンケ80%→特典88%→**予約14%**。通常30%なので此処が詰まり）
  - ch9 SQLで出す（`COUNT(*)` / `COUNT(DISTINCT user_id)` / `HAVING COUNT(*) >= 2` でリピート）
  - ch10 GMV目標から逆算 / ch11 予実・属性×ファネル / ch12 施策を洗い出し→工数×インパクト
- **「Stripe ConnectのGMVを3.9倍にした話」**（`content=91c78f12…`／第2回ch13）= 合宿のお手本になる実例。各段を1つずつ改善：アクセス **7.4%→23.1%**・カゴ落ち **63.8%→68.9%**・リピート **30%→35%** ＝ 約3.9倍。
- **第1回**（`1.全体像・基礎編.mdx`）= ファネル・キャッシュポイント・ISSUEドリブン・「施策を考える順番」の土台（重複回避用）。
- **Supabaseローカル開発 公式**（環境手順の一次情報）：getting-started / seeding-your-database / cli config。

## 構成案の叩き（手順2 / 添削対象）

> 1日オフライン・ローカルSupabaseエミュレーター前提。第2回ch8〜13を「見る」から「自分でやる」に置き換える。タイムは仮。各ワークは **手を動かす → その場でFB** をセットにする。

### 1日の流れ（仮タイムテーブル）

| 時間 | パート | 受講生がやること |
|---|---|---|
| 0:00–0:30 | **0. 環境構築** | `supabase start` でローカルDB起動、共通シード投入、Studioでテーブルを確認。「全員同じデータが見えている」をゴールに、ここで詰まる人を全員巻き取る |
| 0:30–1:00 | **1. ファネルをSQLで出す** | `COUNT` / `DISTINCT` / `HAVING` で 登録→注文→2回目→3回目 の各段の人数を自分で出す（ch9の再現） |
| 1:00–1:30 | **2. 詰まりを特定する** | 各段を割り算して通過率を出し、「どこが普通より低いか＝詰まり」を自分で言い当てる（ch8） |
| （休憩） | | |
| 1:45–2:30 | **3. GMV目標から逆算** | 現状の通過率を使い「GMVを2倍にするには各段いくつ必要か」を逆算。非現実な段はどれかまで出す（ch10） |
| 2:30–3:15 | **4. 施策を洗い出し→優先度** | 特定した詰まりに対し施策を質より量で洗い出し、工数×インパクトで優先度づけ→上位1手を決める（ch12） |
| 3:15–3:45 | **5. 発表・相互FB** | 「どこが詰まり／なぜ／明日からやる1手」を各自発表、平田さんが講評 |
| 3:45–4:00 | **6. 持ち帰り** | 同じ型を自分の現場（会社のDB）でやる宿題化。Stripe実例（3.9倍）を改めて見せて「掛け算で効く」を腹落ちさせる |

### 応用（時間が余った／レベルが高い場合）

- 予実管理：予測した通過率と実数のギャップを出す（ch11）
- 属性×ファネル：`orders × users` でどの客層がリピート／離脱しているかを切る（ch11）

### 設計上の論点（添削してほしい観点）

- **環境構築のハードルをどこまで吸収するか**：Docker未導入・Supabase CLI未導入の人をどう巻き取るか。事前課題で各自セットアップ済みにして当日は確認だけにするか／当日0:00–0:30で全員一斉に立てるか。
- **シードデータの作り込み度**：第2回の数字（予約14%、リピート30%等）を再現する「詰まりが仕込まれた」データにするか。属性×ファネルまでやるなら `users` に属性列を持たせるか。
- **ワークの自由度**：模範クエリを先に渡すか／まず自力で書かせて詰まったら出すか（後者の方が「できる」に効くが時間が読みにくい）。
- **1日で14%→の改善「実装」まで踏み込むか**：合宿は「詰まり特定〜施策優先度」までに絞り、実装（機能を作る）は宿題にする想定でよいか。
- **発表のアウトプット形式**：口頭か、簡単なファネル表（Studioのスクショ＋通過率）を各自まとめさせるか。
