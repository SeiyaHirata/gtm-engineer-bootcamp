## 1. 4つの詰まりの正解と根本原因

ReServeの経営課題は「両側から漏れるバケツ」。新規契約（登録＝初月課金500）は来ているのに、月額サブスクと予約決済1%手数料が伸びない。原因は**店舗側2つ＋ユーザー側2つ＝4つの詰まり**。リピート45%は健全で課題ではない。

| 区分 | 場所 | 観測値 | 通常値 | 根本原因 | 見つけ方（SQLの割り算） |
|---|---|---|---|---|---|
| ① 副次 | 管理：登録→設定完了 | **56%** | 80% | **初期設定のUI/UXがわかりづらい**（入力項目が多い・順序が迷子・進捗表示なし） | `is_setup_done` 280 ÷ 登録500 |
| ② 中核 | 管理：2ヶ月→3ヶ月継続 | **50%** | 85% | 予約が実質回らず店舗がうんざり→解約（主因は③a＋③b） | `period_month=3` の店舗89 ÷ `period_month=2` の店舗178 |
| ③a 中核 | ユーザー：訪問→初回予約 | **12%** | 25% | **予約フォームが重い＋送信CTAがボタンに見えない**（テキストリンク風） | 初回予約4,800 ÷ 訪問40,000（定数） |
| ③b 中核 | ユーザー：初回予約→来店確定 | **45%** | 80% | **後払いで金銭コミットがなくキャンセルしやすい**（キャンセル率55%） | `confirmed` 2,160 ÷ 初回予約4,800。`cancelled` は2,640件 |
| ✓ 健全 | ユーザー：初回来店→リピート | **45%** | 45%（標準） | 課題ではない。リピート導線は壊れていない | リピーター875（HAVING COUNT(*)>=2） |

### 因果の鎖（これが答え）

- **②の根本原因は③a＋③b** — 店舗が3ヶ月目に続けない理由は、予約が実質つながっていないから。初回予約自体が少ない（③a）うえ、入った予約もキャンセルばかり（③b）で、店舗は「ReServe使っても予約が回らない」と感じて解約する。
- **③a** — 初回予約フォームの入力項目が多すぎる＋送信CTAがボタンに見えない（下線付き青文字のテキストリンク風）。店舗ページには訪問するが、予約完了まで至らない。
- **③b** — ReServeは後払い（予約時点で決済なし・来店時に支払い）。金銭コミットがないためキャンセル率が異常に高い（確定率45%＝キャンセル率55%）。
- **①は別レイヤー** — そもそも初期設定を完了できない店舗は公開以前に止まる。登録→設定完了の段で離脱が集中（500→280）。
- **リピート45%は健全** — 業界標準どおり。問題の本丸は初回の獲得（③a）とキャンセル（③b）。

## 2. 各段を出す模範SQL

> 環境：ローカルSupabaseエミュレーター。`COUNT` / `DISTINCT` / `HAVING` / `GROUP BY` / `SUM` / `AVG` / `WHERE status=...` の範囲で全段を出せる。
> **訪問40,000は定数**（テーブルなし）。SQLでは出ず、割り算の分母として与える。

### 2-1. 店舗側ファネル（stores と billing_periods）

オンボーディング段（設定・公開）は `stores`、課金継続は `billing_periods` から数える。**継続を `stores` で見ないこと**。

```sql
-- 設定完了（280）★①の分子
SELECT COUNT(*) FROM stores WHERE is_setup_done;

-- 公開（198）
SELECT COUNT(*) FROM stores WHERE is_published;

-- 登録＝初月課金（500）= billing_periods の period_month=1
SELECT COUNT(DISTINCT store_id) FROM billing_periods
WHERE period_month = 1 AND status = 'paid';

-- 2ヶ月目継続（178）
SELECT COUNT(DISTINCT store_id) FROM billing_periods
WHERE period_month = 2 AND status = 'paid';

-- 3ヶ月目継続（89）= 当月MRRの母数
SELECT COUNT(DISTINCT store_id) FROM billing_periods
WHERE period_month = 3 AND status = 'paid';
```

**通過率（★①と★②）**

```sql
-- ① 登録→設定完了（56%）
SELECT (SELECT COUNT(*) FROM stores WHERE is_setup_done)::float
       / (SELECT COUNT(DISTINCT store_id) FROM billing_periods
          WHERE period_month = 1 AND status = 'paid');
-- → 0.56

-- ② 2ヶ月目→3ヶ月目（50%）
SELECT
  (SELECT COUNT(DISTINCT store_id) FROM billing_periods
   WHERE period_month = 3 AND status = 'paid')::float
  / (SELECT COUNT(DISTINCT store_id) FROM billing_periods
     WHERE period_month = 2 AND status = 'paid');
-- → 0.5
```

### 2-2. ユーザー側ファネル（reservations と payments）

> **基準に注意（最重要）** — ユーザー側は「訪問→初回予約→**来店確定**→**初回来店**→リピート」という**初回客の一本道**。`来店確定`・`初回来店` は**初回コホート（各ユーザーの最初の予約／最初の来店）**で数える。`reservations` 全体の `confirmed`（4,785）や `checkins` 全体（4,569）には**リピート分が混ざる**ため、そのままファネル段に使うと数字がズレる。

```sql
-- 初回予約を完了した利用者（4,800）★③aの分子
SELECT COUNT(DISTINCT user_id) AS "初回予約"
FROM reservations WHERE user_id <= 4800;                                  -- → 4,800

-- 来店確定（初回予約のうち確定＝2,160）★③bの分子
--   各ユーザーの「最初の予約」だけを見て confirmed を数える（堅牢）
SELECT COUNT(*) AS "来店確定"
FROM (
  SELECT DISTINCT ON (user_id) status
  FROM reservations
  ORDER BY user_id, created_at
) first_res
WHERE status = 'confirmed';                                              -- → 2,160
--   ※このシードでは初回予約は id 1..4800。簡易には次でも同じ：
--     SELECT COUNT(*) FROM reservations WHERE status='confirmed' AND id <= 4800;  -- 2,160

-- 初回来店（初回コホートの来店＝1,944）
--   各ユーザーの「最初の来店」だけを数える
SELECT COUNT(*) AS "初回来店"
FROM (
  SELECT DISTINCT ON (user_id) id
  FROM checkins
  ORDER BY user_id, checked_in_at
) first_visit;                                                           -- → 1,944

-- （参考・ファネル段ではない）全予約の確定・キャンセル
SELECT COUNT(*) AS "予約確定数_全体" FROM reservations WHERE status='confirmed';  -- 4,785（初回2,160＋リピート2,625）
SELECT COUNT(*) AS "キャンセル数"   FROM reservations WHERE status='cancelled';  -- 2,640（全件が初回予約由来＝③b）

-- ③a 訪問→初回予約（12%）。訪問40,000は定数
SELECT 4800.0 / 40000 AS "③a_初回予約率";   -- → 0.12

-- ③b 初回予約→来店確定（45%＝キャンセル率55%）。来店確定2,160 ÷ 初回予約4,800
SELECT 2160.0 / 4800 AS "③b_来店確定率";    -- → 0.45
```

> **③bの数え方の注意（受講生がここで詰まる）** — `status='confirmed'` の全件は4,785（リピート2,625を含む）。これを来店確定だと思うと2,160と合わず混乱する。③bの確定率45%は**初回予約4,800を母数に、初回分の confirmed 2,160**で割る。`cancelled` 2,640件は全件が初回予約由来（リピート予約は全 confirmed）なので、`2,160 ÷ (2,160+2,640) = 0.45` でも一致する。

### 2-3. リピーター875（HAVING COUNT(*)>=2）

来店＝決済。`payments` を `user_id` で集計し、2回以上決済した利用者をリピーターとする。

```sql
-- リピーター人数（875）
SELECT COUNT(*) AS "リピーター" FROM (
  SELECT user_id FROM payments
  GROUP BY user_id
  HAVING COUNT(*) >= 2
) r;
-- → 875

-- 初回来店→リピートの率（45%・健全）。初回来店1,944が母数（→ 2-2）
SELECT 875.0 / 1944 AS "リピート率";   -- → 約0.45
```

### 2-4. キャッシュポイント（GMV・手数料・サブスク）

```sql
-- 平均決済単価（4,000）と GMV（18,276,000）
SELECT AVG(amount) AS "平均単価", SUM(amount) AS "GMV" FROM payments;

-- 月間手数料収益（GMV × 1% = 182,760）
SELECT ROUND(SUM(amount) * 0.01) AS "手数料収益" FROM payments;

-- 単価特定（12,000。全行同一を DISTINCT で確認）
SELECT DISTINCT amount FROM billing_periods;   -- → 12,000

-- 当月サブスク収益（3ヶ月目継続89 × 12,000 = 1,068,000）
SELECT COUNT(DISTINCT store_id) * (SELECT DISTINCT amount FROM billing_periods)
FROM billing_periods
WHERE period_month = 3 AND status = 'paid';
-- → 1,068,000
```

- **決済件数の内訳**：初回来店決済1,944件 ＋ リピーター875人×3回＝2,625件 ＝ 合計4,569件。
- **月間ReServe収益合計**：サブスク1,068,000 ＋ 手数料182,760 ＝ **1,250,760円**。

### 2-5. シード検算（講師用・一括）

> データの**総件数**の検算（リピート込み）。`予約確定数_全体`=4,785・`来店数_全体`=4,569 は**総数**で、ファネルの来店確定2,160／初回来店1,944とは**別物**（→ ファネルの答え合わせは §2-6）。

```sql
SELECT
  (SELECT COUNT(*) FROM stores)                                          AS "登録店舗数",
  (SELECT COUNT(*) FROM stores WHERE is_setup_done)                      AS "設定完了店舗数",
  (SELECT COUNT(*) FROM stores WHERE is_published)                       AS "公開店舗数",
  (SELECT COUNT(DISTINCT store_id) FROM billing_periods
   WHERE period_month=2 AND status='paid')                               AS "2ヶ月継続店舗数",
  (SELECT COUNT(DISTINCT store_id) FROM billing_periods
   WHERE period_month=3 AND status='paid')                               AS "3ヶ月継続店舗数",
  (SELECT COUNT(DISTINCT user_id) FROM reservations
   WHERE user_id <= 4800)                                                AS "初回予約ユーザー数",
  (SELECT COUNT(*) FROM reservations WHERE status='confirmed')           AS "予約確定数_全体",
  (SELECT COUNT(*) FROM reservations WHERE status='cancelled')           AS "キャンセル数",
  (SELECT COUNT(*) FROM checkins)                                        AS "来店数_全体",
  (SELECT COUNT(*) FROM (
    SELECT user_id FROM payments GROUP BY user_id HAVING COUNT(*)>=2) r)  AS "リピーター数",
  (SELECT SUM(amount) FROM payments)                                     AS "総流通額GMV",
  (SELECT ROUND(SUM(amount)*0.01) FROM payments)                         AS "手数料収益";
```

**期待値**：500 / 280 / 198 / 178 / 89 / 4800 / 4785 / 2640 / 4569 / 875 / 18276000 / 182760。

### 2-6. 答え合わせ（ファネル段・一括）

> §2-5 は**総件数の検算**（リピート込み）。**ファネルの答え合わせ**はこちら——初回コホート基準で各段を出す。受講生が描いたファネルの数字はこの結果と一致させる。

```sql
SELECT
  (SELECT COUNT(DISTINCT store_id) FROM billing_periods WHERE period_month=1 AND status='paid') AS "登録",
  (SELECT COUNT(*) FROM stores WHERE is_setup_done)                          AS "設定完了",
  (SELECT COUNT(*) FROM stores WHERE is_published)                           AS "公開",
  (SELECT COUNT(DISTINCT store_id) FROM billing_periods WHERE period_month=2 AND status='paid') AS "2ヶ月継続",
  (SELECT COUNT(DISTINCT store_id) FROM billing_periods WHERE period_month=3 AND status='paid') AS "3ヶ月継続",
  40000                                                                       AS "訪問_定数",
  (SELECT COUNT(DISTINCT user_id) FROM reservations WHERE user_id<=4800)      AS "初回予約",
  (SELECT COUNT(*) FROM (SELECT DISTINCT ON (user_id) status FROM reservations ORDER BY user_id, created_at) f WHERE status='confirmed') AS "来店確定",
  (SELECT COUNT(*) FROM (SELECT DISTINCT ON (user_id) id FROM checkins ORDER BY user_id, checked_in_at) f)                              AS "初回来店",
  (SELECT COUNT(*) FROM (SELECT user_id FROM payments GROUP BY user_id HAVING COUNT(*)>=2) r) AS "リピーター";
```

**期待値**：500 / 280 / 198 / 178 / 89 / 40000 / 4800 / 2160 / 1944 / 875。

## 3. ROI模範9案（Before/After差分）

### 計算の共通ルール（再掲）

- **工数の単位は時間（h）**。**時給5,000円/時間**。**コスト＝工数（時間）× 5,000円**。
- **ROI＝年間リターン ÷ コスト（倍）**。
- **リターンは2軸（混ぜない）**
  - 管理画面側（①②）＝（増えた**3ヶ月目継続店舗数**）× 12,000円 × 12ヶ月
  - ユーザー側（③a③b）＝（増えた**来店決済件数**）× 4,000円 × 1% × 12ヶ月
- **インパクトは必ずファネルで読む** — 改善した段の%だけ書かず、下流の各段のBefore/After/差分を出してからリターンにする。
- **下流係数（施策後もこの通過率を使う）**
  - ① 設定完了→3ヶ月継続：× 公開71% × 2ヶ月90% × 3ヶ月50% ＝ **×0.3195**
  - ③a 初回予約→来店決済：× 来店確定45% × 来店90% ＝ **×0.405**
  - ② 2ヶ月継続→3ヶ月継続：× 3ヶ月通過率のみ（母数＝178）
  - ③b 初回予約→来店確定：初回予約4,800を母数に据え置き、確定率だけ変える

## 4. 模範優先度（全体）

**今週40時間（20万円）の予算**しか使えないときの模範解。

| 優先 | 施策 | 工数 | 理由 |
|---|---|---|---|
| **第1** | ①ステップガイド | 16時間 | ROI 45倍。半日強でサブスクが積み上がる |
| **第2** | ③a CTAボタン化 → フォーム簡素化 | 4h＋8h | モックで気づく即効UX（8倍）＋項目削減（7.8倍）。合計28時間 |
| **第3** | ③bキャンセル料表示 | 2時間 | 2時間・1万円でROI 10倍。デポジット（48h・1.7倍）より圧勝 |
| 様子見 | ①入力項目整理 | 32時間 | ROI 34倍だが効果検証後。ガイドで足りなければ次 |
| 後回し | ②解約防止クーポン | 12時間 | ROI 34倍に見えるが、③を直さないと**再発**。対症療法 |
| 後回し | ③bデポジット | 48時間 | 効果は大きいが決済改修は1週間。ROI 1.7倍で投資判断は微妙 |

### ②クーポンとデポジットの「罠」

- **②に直接投じる施策はファネル上+14店に見えても、③を直さないと持続しない** — 解約クーポンは2ヶ月継続178を母数に+14店ときれいに見えるが、予約が回っていない店舗（③a/③b未改善）にクーポンを出しても、翌月以降に再解約する。**持続性はファネル表だけでは読めない**（因果の話）。②の主因は③a＋③bなので、根本原因（③）に投資するのが正しい。
- **③bデポジットは効果は大きいがコストでROIが負ける** — 来店+864件はキャンセル料表示（+216件）の4倍だが、工数は48h vs 2h、決済連携はAIでも縮まない。ファネルで読むと効果は大きいが、ROIは1.7倍 vs 10倍でキャンセル料表示に負ける。

### 受講生に言わせたい発見（ワークの核）

1. **リターンの2軸の桁差** — ①は+26店＝374万、③aは+648件＝31万。ファネルで下流まで追うと桁差が体感できる。
2. **同一詰まり内でROIが逆転** — ③bで来店+864件（デポジット）vs +216件（文言2h）。効果4倍でもROIは1.7倍 vs 10倍。
3. **②へ直接投じる施策の罠** — ファネル上+14店に見えても、③を直さないと持続しない。
4. **40時間の予算で第1〜第3まで全部やれる** — 16＋12＋2＝30時間（第1①16h＋第2③a計12h＋第3③b 2h）。工数制約内で順序を決める。

## 5. 講評で見るポイント

評価ルーブリック（①課題特定25／②キャッシュポイント15／③施策洗い出し15／④ROI算出25／⑤優先度結論15／⑥プレゼン5）に沿って、特に以下の落とし穴を見る。

- **モックの数字から答えていないか** — ダッシュボード（A-03）のキャンセル18件等は**演出用の仮数**。DBの2,640件・通過率45%とは無関係。「ダッシュボード見たらキャンセル多いから③b」はNG。詰まりの特定は必ず `reservations` の `status` を**SQLで数える**。受講生がモックの数字から詰まりを答えたら不合格扱いに近い（FBでSQLに戻す）。
- **改善%だけで止まっていないか** — ④は改善%から**ファネル各段のBefore/After/差分**を出し、最終段の差分→年間リターン→ROIの順で計算しているか。改善%だけ書いて下流の件数差分を出さないのはNG。
- **2軸のリターンを混ぜていないか** — 管理側（①②）は3ヶ月継続×12,000×12、ユーザー側（③a③b）は来店決済×4,000×1%×12。混同していないか。
- **全体ROI順で優先度を語っているか** — 「自分のチームの詰まり＝最優先」と決めつけず、**全体表の上位（ROI順）から**第1・第2・第3を説明しているか。①が③より先、等のROIの逆転を数字で言えているか。
- **③→②の因果を説明できているか** — ②（3ヶ月目解約）の主因は③a＋③b。②単体のクーポンが再発する理由を、ROIの数字と矛盾なく説明できているか。
- **ファネル下流まで計算しているか** — ①は設定完了→公開71%→2ヶ月90%→3ヶ月50%（×0.3195）、③aは初回予約→来店確定45%→来店90%（×0.405）まで波及させてから最終段の差分を取っているか。
- **リピート45%を課題扱いしていないか** — リピートは業界標準で健全。ここを「詰まり」として施策を立てていたら、本丸（③a・③b）に戻す。
